# 130. PART N — The second review: the universal algorithm as code

A second reviewer compared the guide against the original requirement — "given a new model, derive Modality → Architecture → Task → Input/Output → Processor → Collator → Loss → Trainable modules → PEFT → Data → Trainer → Evaluation → Export → Serving" — and concluded that roughly 70-80% was there, with the missing part being **the universal layer itself**.

## 130.1 First, what the review measured

That review read the **215-page edition** (its page count and its quotes from the old compatibility table). Parts J-M — vision, audio, multimodal, MoE, SSM/RNN, diffusion, custom architectures, the task registry — were added afterwards and answer most of its "❌" rows. What it identified that was **genuinely absent as code**, in its own words:

|Missing item|Status now|
|---|---|
|Universal **Processor** abstraction|**built**: `uadapt/processors.py` (chapter 131)|
|Universal **Loss derivation**|**built**: `uadapt/derive.py` (chapter 133)|
|Universal modality-independent **trainer design**|**built**: `uadapt/pipeline.py` over `uadapt/loop.py` (chapter 134)|
|Universal **architecture adapter layer**|**built**: adapter strategy with graceful degradation (chapter 134.3)|
|"Future unseen modality: conceptually, not practically demonstrated"|**demonstrated**: an invented modality trained end to end (chapter 135)|
|First-principles derivation per family (its BERT example)|**chapter 132**, generated by the tool|

## 130.2 The claim this part adds

Before Part N the book told you *what to do* for each family. Now the engine **derives** it:

```text
model + one batch
   -> modality and architecture      (evidence)
   -> input contract                 (observed shapes and dtypes)
   -> output contract                (what the numbers MEAN: vocabulary? classes? a value? embeddings?)
   -> LOSS, with rationale and confidence, or an honest "CUSTOM ENGINEERING REQUIRED"
   -> trainable modules + adapter strategy (degrading when LoRA cannot reach the weights)
   -> processor (found, or the contract you implement)
   -> task, and the metrics that task must report
   -> smoke test -> train -> export with a merge proof -> serving plan
```

Three things are never derived, because no framework can invent them: **your data**, **your definition of success**, and — for a modality nobody has built before — a **processor `encode()`** and possibly a **loss function**. The engine now states exactly which of those are missing for the model in front of you, instead of failing later.
